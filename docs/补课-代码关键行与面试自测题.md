# 补课：Agent 核心代码关键行 + 面试自测题答案

> 代写模式交付后的补课材料。面试被问"你的代码怎么实现的"时，照这里的思路答。

## 一、agent.py 主循环关键行

### 1. 出口判断（agent.py 第 52 行）
```python
if not msg.tool_calls:
    return AgentResult(answer=msg.content or "", tool_trace=tool_trace)
```
**为什么这么写**：模型没有返回 `tool_calls`，说明它认为信息够了，给出最终答案。
这是 ReAct 循环的**唯一正常出口**。`tool_calls` 为 None 或空列表都进这里。

### 2. assistant 消息回填（agent.py 第 58-63 行）
```python
messages.append({
    "role": "assistant",
    "content": msg.content,
    "tool_calls": [tc.model_dump(exclude_none=True) for tc in msg.tool_calls],
})
```
**关键点**：必须把模型声明的 `tool_calls` **原样回填**进 assistant 消息。
下一轮请求时，API 要靠这条消息验证"你之前说要调这些工具"的上下文完整性。
漏掉这步会报 "tool_calls did not match expected message" 错误。

`model_dump(exclude_none=True)`：把 SDK 的 Pydantic 对象转成 dict，排除 None 字段。

### 3. tool 消息配对（agent.py 第 73-75 行）
```python
messages.append({"role": "tool",
                 "tool_call_id": tc.id,
                 "content": result})
```
**关键点**：每条 tool 消息的 `tool_call_id` 必须和 assistant 消息里的 `tc.id` 配对。
一个 assistant 声明 3 个 tool_call，就必须有 3 条 tool 消息，id 一一对应。
不配对会报 "expected tool message but got none" 或乱序。

### 4. 三层防御链（agent.py 第 86-109 行 `_execute_tool`）
```python
# 防御 1：arguments 是 JSON 字符串，可能不合法
try: params = json.loads(raw)
except json.JSONDecodeError: return error_json

# 防御 2：模型可能幻觉出不存在的工具名
tool = self.tool_map.get(name)
if tool is None: return error_json

# 防御 3：工具执行可能抛异常
try: return tool.call(params)
except Exception: return error_json
```
**设计哲学**：任何一层失败都**不中断循环**，把错误作为 observation 回传。
模型看到 "参数不是合法 JSON" 会自己修正参数重试——这就是 Agent 自愈。

### 5. max_turns 兜底（agent.py 第 79-82 行）
```python
messages.append({"role": "user",
    "content": "信息收集已达上限，请基于已有信息直接给出总结回答。"})
resp = self.llm.chat(messages)  # 注意：不传 tools
```
**关键点**：到顶后**不带 tools** 再调一次，强制模型给文字答案而非继续调工具。
否则模型可能继续循环（"我还想再查一个日志"），死循环。

## 二、router.py 决策路由关键行

### 1. RAG 作为路由信号（router.py 第 60-64 行）
```python
rag_raw = self.rag_tool.call({"query": user_message, "top_k": 3})
rag = json.loads(rag_raw)
sim = rag.get("best_sim", 0.0)
```
**设计点**：Router **直接调** RAG 工具（不经 LLM），拿 sim 分数做决策。
RAG 工具有双重身份：① 路由信号源 ② Agent 工具池的一员。

### 2. 三分支阈值判定（router.py 第 70-77 行）
```python
if sim >= self.sim_high and kw_cov >= self.kw_coverage_low:   # ≥0.70 且 ≥0.30
    return self._route_rag_direct(...)
if sim >= self.sim_low:                                        # ≥0.45
    return self._route_agent_loop(...)
return self._route_refuse_human(...)                            # <0.45
```
**面试答法**：高置信走 RAG 直答（省 token，不进循环）；
中置信走 Agent 循环（工具补充信息）；低置信拒答转人工（防幻觉）。

### 3. RAG 先验注入 Agent（router.py 第 102 行）
```python
prior = f"\n\n[知识库先验，相似度 {sim:.2f}] {kb_hits[0]['text']}"
enriched_query = query + prior
result = self.agent.run(enriched_query, history=history)
```
**关键点**：中置信路径把 RAG 命中片段塞进 query，让 Agent 在已知信息基础上
决定是否还要调工具——避免重复检索，也避免 Agent 从零开始。

## 三、面试自测题答案

### Q1: tool_call_id 为什么必须配对？
**答**：OpenAI 兼容 API 要求 assistant 消息声明的每个 tool_call，都必须有对应的
tool 消息回填结果，靠 id 配对。不配对会报错，因为 API 要验证"你说的调用是否
都有结果"。多个并行 tool_call 时，id 顺序也要对应。

### Q2: max_turns 到顶怎么处理？
**答**：不带 tools 再调一次 LLM，强制基于已有信息给文字总结。
不这样做的话，模型可能继续返回 tool_calls，循环不结束。
这是"防止 Agent 死缠烂打"的工程兜底。

### Q3: Python 循环导入怎么解决？
**答**：三种方法：① 底部 import（本项目用的，`from tools import example`
放 `__init__.py` 末尾，等 register_tool 定义完再触发）；② 函数内延迟 import；
③ 重新设计模块职责，把循环依赖拆开。本项目踩过这个坑：example.py 顶部
`from tools import register_tool`，而 `__init__.py` 顶部就 import example，
形成 tools→example→tools 的死亡链条。

### Q4: Function Calling 中模型执行了函数吗？
**答**：没有。模型只做两件事：① 判断意图（该调哪个工具）② 生成参数（JSON）。
真正执行的是**我写的 Agent 循环**：解析 tool_calls → `TOOL_REGISTRY[name].call(params)`
→ 拿结果 → 回填 messages。模型从头到尾没碰过任何系统权限。这就是 Function
Calling 的安全模型：模型只能"提请求"，执行与否、执行什么，控制权全在应用侧。

### Q5: 你的 Agent 是 ReAct 吗？
**答**：循环结构是 ReAct 的（think→act→observe 交替、观察驱动下一轮决策），
但工具调用协议用的是现代 Function Calling 而非论文 2022 年的停用词文本解析。
区别：ReAct 原版靠检测 `Action:` 停用词截断生成，推理模型的中间思维可能
撞上停用词导致提前截断；`<tool_call>` 标签（Function Calling）闭合解析更稳。

### Q6: 为什么 description 要写"什么时候用"而不是"是什么"？
**答**：模型选工具靠的是 description 和问题语义的匹配度（训练对齐学的）。
写"是什么"（如"日志查询工具"）模型只懂功能；写"什么时候用"（如"当用户
询问服务报错、故障排查时调用"）模型能匹配使用场景。这直接决定工具选择
准确率——是第 4 周评估里"工具选择准确率"指标的优化杠杆。

### Q7: 为什么 RAG 工具有双重身份？
**答**：① 被 Router 直接调——拿 sim 分数做路由决策（高置信直答/中置信走Agent/低置信拒答）；
② 被 Agent 调——作为工具池一员，给 LLM 看检索到的知识片段。
这两次调用目的不同：第一次是"要不要进循环"的信号，第二次是"循环里要不要查知识"。

## 七、意图检测优化实验（v1 vs v3，真实数据）

> 这是项目里最值得在面试时讲的故事：发现真实缺陷 → 修复 → 数据反超 → 暴露新权衡。
> （注：v2 因先验注入 bug 被问题19修复取代，不作为对比基线；v3=扩充意图+先验门控修复，是最终版）

### 缺陷发现

真实 API 跑 verify.py 时，第三条"查一下 nginx 最近的报错日志"被路由到 refuse_human
（sim=0.29 < 0.45），但用户意图明显是"查日志"——Agent 该处理。

**根因**：路由决策完全靠 RAG 相似度。KB 是知识型内容（nginx 502 怎么排查/OOM 处理），
没有"查/执行/诊断"这类动作描述。动作型查询（查日志/查监控/查进程）和 KB 语义距离远，
sim 天然偏低，被误判到 refuse_human。

### 修复：意图检测层（router.py `_detect_intent`）

```python
# 只在 sim < sim_low（本要 refuse_human）时触发，不干扰高/中置信路径
if sim >= self.sim_high and kw_cov >= self.kw_coverage_low:
    return self._route_rag_direct(...)      # 高置信，KB 直答
if sim >= self.sim_low:
    return self._route_agent_loop(...)      # 中置信，走 Agent
# ↓ 低置信，本要拒答，先过意图检测兜底
if self._detect_intent(user_message):
    return self._route_agent_loop(...)      # 救回 agent_loop
return self._route_refuse_human(...)        # 真拒答
```

意图检测用"动作词 + 主题词"双命中（`_ACTION_VERBS` + `_TOOL_THEMES`），
避免单命中过激（"查一下天气"只有动作词无主题词→不救；"nginx 502 是什么"
若 sim 高走 rag_direct 根本到不了这层）。

### v1 vs v3 数据对比（20 题 × 2 基线，真实 API，v3=最终版）

| 指标 | AGENT v1（窄意图） | AGENT v3（扩充意图+先验门控） | RAG |
|---|---|---|---|
| answer_score_avg | 0.875 | **0.975** ✅ | 0.975 |
| tool_accuracy_avg | 0.450 | **1.000** | 0 |
| param_accuracy_avg | 0.450 | 0.925 | 0 |
| turns_avg | 1.200 | 3.950 | 0 |
| latency_ms_avg | 1879 | 5382 | 2193 |
| 路由分布 | 多数 refuse | 16 agent_loop / 2 refuse / 2 rag_direct | — |

> **版本演进**：v1=窄意图；v2=扩充意图但先验注入有 bug（turns 4.85/latency 6353，见问题19）；
> v3=扩充意图+先验注入门控修复（turns 3.95/latency 5382，最终版，报告页展示此数据）。

**关键洞察**：
- 意图检测救回 14 道题（refuse→agent_loop），agent answer 从 0.875 反超到 0.975
- 救回的题全部调对工具（tool_accuracy 0.45→1.000），说明意图检测精准
- **代价是约 2.9 倍延迟**（1879→5382ms）：救回的题要走完整 Agent 循环（平均 3.95 轮工具调用）
- RAG 在知识型问题上仍最快最稳（0.975 / 2193ms），但答不了动作型（tool_accuracy=0）

### 面试讲法（3 分钟版）

> 我跑三基线评估时发现一个真实缺陷：路由决策完全靠 RAG 相似度，但 KB 是知识型内容，
> 对"查日志/查监控"这类动作型查询打分偏低（sim 0.29），被误判到拒答转人工。
> 我加了意图检测层——用"动作词+主题词"双命中兜底，只在低置信（本要拒答）时触发，
> 不干扰高/中置信路径。修复后 agent answer 从 0.875 反超到 0.975，tool_accuracy
> 从 0.45 到 1.000。代价是约 2.9 倍延迟——这是准确率/延迟权衡的经典案例，生产化时
> 要按业务 SLA 决定救不救、救多少。（后续修先验注入 bug 还把延迟从 6353 降到 5382，见问题19）

### Q8（新增）：为什么意图检测用双命中而不是单命中？
**答**：单命中过激。"查一下天气"只有动作词无主题词，不该走 agent；
"nginx 502 是什么"若 sim 高走 rag_direct 根本到不了意图检测层，但若 sim 低，
有主题词无动作词（"是什么"算问句不算动作）也不该强救。双命中（动作+主题）
保证只救"明确要执行运维动作"的查询，是精度/召回的折中。

### Q9（新增）：延迟怎么优化？
**答**：三个方向：① 并行 tool_calls（模型一轮可声明多个工具，现在串行执行）；
② 工具结果缓存（同 query 短期内复用）；③ 分级 SLA——知识型走 RAG 快答，
动作型走 Agent 慢答，前端用 SSE 流式让用户感知"在干活"而非"在等"。
我的项目里 ②③ 都做了（rag_search 有缓存、SSE 流式输出），① 是下一步优化点。
另外问题19的先验注入门控修复也意外降了 15% 延迟（噪声先验会让 Agent 多花轮次处理）。
