## 一、开发过程问题全记录（按时间线）

### Week 1 Day 1：LLMClient 封装

#### 问题 1：OpenAI 客户端创建完没保存引用

**现象**：`cli.py` 跑起来报 `AttributeError: 'LLMClient' object has no attribute 'client'`，明明 `__init__` 里写了 `OpenAI(...)`。

**排查**：打开 `llm_client.py` 看 `__init__`：
```python
def __init__(self, api_key, base_url, model):
    OpenAI(base_url="https://api.deepseek.com", api_key=DEEPSEEK_API_KEY)  # ← 创建了没接住
```
这行调用了 `OpenAI()` 构造函数，但返回的对象没赋值给任何变量，创建完就被垃圾回收了。后面 `chat()` 里 `self.client.chat...` 自然拿不到。

而且这里硬编码了 `base_url` 和全局 `DEEPSEEK_API_KEY`，构造函数收的三个参数一个都没用——两套逻辑打架。

**解法**：
```python
def __init__(self, api_key, base_url, model):
    self.client = OpenAI(api_key=api_key, base_url=base_url)
    self.model = model  # chat 里要用，先存下来
```
参数从外面传进来（Day 3 在 `cli.py` 组装时再从 `config` 读），`LLMClient` 本身保持通用——这样第 2 周想切 Qwen API 时只改传参，不改这个类。

**教训**：构造函数里的对象一定要赋给 `self.xxx`，否则就是一次性消费。这是"实例属性 vs 局部变量"的基本区分，但调试时容易盯半天。

### Week 1 Day 2：工具基类、注册表、schema 转换

这一天的坑最多，全是 Python 机制层面，面试官最爱问。

#### 问题 2：循环导入（`tools/__init__.py` 顶部 import）

**现象**：`python -c "import tools"` 直接崩，报 `ImportError: cannot import name 'register_tool'`。

**排查**：把 import 写在了 `tools/__init__.py` 顶部（第 1 行），追死亡链条：
```
import tools
 → 执行 tools/__init__.py 第 1 行: from tools import example
   → 执行 example.py 第 2 行: from tools import register_tool
     → 此时的 tools 模块只执行到第 1 行，register_tool 还没定义！
       → ImportError
```

**解法**：把 `from tools import example` 挪到文件**最底部**（`register_tool` 定义之后）。Python 允许底部 import，这是打破循环导入的标准手法之一。

**面试标准答案**：Python 循环导入有三种解法——① 底部 import（我用的）；② 函数内延迟 import；③ 重新设计模块职责（把共享的东西提到独立模块）。我选底部 import 是因为注册表和工具模块职责清晰，只是初始化顺序问题，不想为了顺序再拆模块。

#### 问题 3：抽象类实例化报错（`@abstractmethod`）

**现象**：`QueryLogTool` 写了外壳（name/description/parameters 都对），但 `call` 方法没写，import 时直接报：
```
TypeError: Can't instantiate abstract class QueryLogTool
without an implementation for abstract method 'call'
```

**排查**：`BaseTool` 里的 `call` 用 `@abstractmethod` 装饰，是**强制契约**：子类不实现就不允许实例化。而我的 `register_tool` 装饰器里就执行了 `cls()`，所以 import 的一瞬间炸了。

**解法**：补齐 `QueryLogTool.call` 实现。

**教训**：这其实是好事——错误在注册时就暴露，而不是等到运行中途才炸。这就是抽象基类存在的意义：把"忘写 call"从运行时隐患变成 import 时报错。面试被问"为什么要用抽象基类"就这么答。

#### 问题 4：`required` 在循环里被反复覆盖

**现象**：`to_openai_schema` 跑出来，工具的 `required` 字段是空列表，明明有必填参数 `keyword`。

**排查**：看代码：
```python
for p in tool.parameters:
    properties[p["name"]] = {"type": p["type"], "description": p["description"]}
    required = [p["name"]] if p.get("required", False) else []  # ← 在循环里
```
`required` 每循环一次就被**重新赋值**，循环结束时只剩最后一个参数的结果。推演：
```
参数列表: [keyword(required=True), hours(required=False)]
循环第1轮: required = ["keyword"]
循环第2轮: required = []           ← 覆盖了！
最终: required = []                ← keyword 丢了
```
模型可能因此不传必填参数，运行时出现"缺参数"的诡异现象。

**解法**：把 `required` 移出循环，放在循环结束后，用列表推导一次生成：
```python
for p in tool.parameters:
    properties[p["name"]] = {"type": p["type"], "description": p["description"]}
required = [p["name"] for p in tool.parameters if p.get("required", False)]
```
判断标准：循环体只该干"每个参数各处理一次"的事（properties）；`required` 是"所有参数处理完汇总一次"的事，必须在循环外。

**面试讲法**：这是"累加 vs 覆盖"的经典坑。循环里要累加得用 `list.append` 或 `+=`，直接赋值 `=` 就是覆盖。改用列表推导既解决覆盖问题，代码也更 Pythonic。

#### 问题 5：工具注册表为空（装饰器没触发）

**现象**：写了两个工具类（WeatherTool、QueryLogTool），都加了 `@register_tool`，但 `TOOL_REGISTRY` 永远是空字典。

**排查**：装饰器只在**类定义代码被执行时**才运行。而类定义只有模块被 import 才执行。我的 `example.py` 写好了，但哪里都没 import 它，里面一行都不会执行，注册表就是空的。

**解法**：在 `tools/__init__.py` 底部加 `from tools import example`，这样任何人 `import tools`，注册就自动发生了。

**教训**：装饰器不是魔法——它是个"类被定义时才触发"的钩子。模块没被 import，里面的 `@register_tool` 一行都不会跑。这是"装饰器触发时机"的认知，面试被问"装饰器什么时候执行"就这么答。

#### 问题 6：`to_openai_schema` 写错文件位置

**现象**：Day 3 写 `agent.py` 时 `from tools.base import to_openai_schema` 拿到的是坏的那份（空壳），debug 半天。

**排查**：`base.py` 里有个空壳 `to_openai_schema`（骨架给的），我又在 `__init__.py` 写了一份半成品。两份定义并存，import 路径决定了拿到哪份。

**解法**：把 `__init__.py` 里的函数剪切到 `base.py`，替换掉空壳；`__init__.py` 只留注册表 + 底部 import。职责分工：
- `tools/base.py`：BaseTool + `to_openai_schema`（转换函数是 BaseTool 的配套，数据和行为放一起）
- `tools/__init__.py`：只留注册表 + 统一出口（单一职责）

**教训**：同名的函数不要在两个文件各定义一份——import 路径决定拿到哪份，debug 时容易怀疑人生。

#### 问题 7：`query_log` 的 `call` 取了参数没用（过滤缺失）

**现象**：注册表两项齐了，但测试 `call({'keyword': 'mysql'})` 返回了全部 6 条日志，nginx 的也混在里面。

**排查**：看 `call` 实现：
```python
def call(self, params: dict) -> str:
    keyword = params["keyword"]
    hours = params.get("hours", 24)
    return json.dumps(MOCK_LOGS, ensure_ascii=False)  # ← keyword 过滤呢？
```
三步只写了两步，**过滤那步丢了**——取了 `keyword` 却没用它。

**解法**：加一行过滤：
```python
logs = [log for log in MOCK_LOGS if keyword.lower() in log.lower()]
```
然后 `json.dumps` 的对象换成处理后的结果。空结果也要返回有内容的 str（`{"result": "未找到相关日志"}`），别返回空列表——模型收到 `[]` 容易瞎编。

**教训**：`call` 是工具的执行体，参数是模型生成的（不可信）。① 必填参数用 `params["key"]`（缺了让它报错，暴露模型问题）；② 可选参数用 `params.get("key", default)`（缺了用默认值，别让 KeyError 炸）。

#### 问题 8：`MOCK_LOGS` 放文件底部

**现象**：代码能跑，但 code review 会被挑。

**排查**：`MOCK_LOGS` 定义在文件底部，`call` 在类里引用它。Python 里这其实能跑（因为 `call` 执行时模块已全部加载），但常量定义在使用处之前是 Python 惯例。

**解法**：`MOCK_LOGS` 挪到 import 语句下面（模块顶部）。

**教训**：能跑 ≠ 写得好。常量、配置放顶部，类定义放中间，入口放底部——这是 Python 文件组织的惯例，code review 印象分。

### Week 1 Day 2 续：RAG 相似度算法调优

#### 问题 9：Jaccard 相似度对中文长文本惩罚过重

**现象**：跑路由测试，`nginx 502 bad gateway 怎么排查` 这种明显高匹配的 query，sim 只有 0.126，远低于阈值 0.70，直接走拒答。

**排查**：原算法用字符 2-gram Jaccard 相似度（`len(A∩B) / len(A∪B)`）。Jaccard 的特性是"惩罚集合差异"——query 短、KB 文本长，并集很大，交集相对小，相似度天然偏低。中文长文本尤其严重（每个字都是 2-gram，并集膨胀快）。

**解法**：改用"query 覆盖率"算法——query 的 n-gram 有多少出现在 KB 文本里：
```python
def _similarity(query: str, text: str) -> float:
    q_grams = _char_ngrams(query)
    t_grams = _char_ngrams(text)
    if not q_grams:
        return 0.0
    return len(q_grams & t_grams) / len(q_grams)  # query 覆盖率，不是 Jaccard
```

**验证**：改完跑真实数据，数值分布合理了：
- `mysql too many connections`(0.792) → 高置信走 rag_direct ✅
- `nginx 502`(0.667) → 中区间走 agent_loop ✅
- `午饭`(0) → 拒答 ✅

**教训**：相似度算法的选择要看业务场景。"两段文本有多像"（Jaccard/余弦）和"query 里的信息 KB 覆盖了多少"（覆盖率）是两个不同问题。运维场景要的是后者——用户问的关键词 KB 里有就行，不需要整句都像。

### Week 1 Day 3：主循环与 Function Calling 原理

#### 问题 10：概念混淆——"模型调用工具"是错的

**现象**：最初理解 Function Calling 时说"模型调用工具，call 执行函数"。

**纠正**：模型**不会调用任何东西**，它只输出一段结构化文本："我要调 query_log，参数是 {keyword: 'nginx'}"——这只是一段声明。真正执行的是**你写的 Agent 循环**：解析 `tool_calls` → `TOOL_REGISTRY[name].call(params)` → 拿结果回填。

**准确的一句话**：模型管"想"（意图识别 + 参数生成），代码管"做"（执行 + 回填），循环管"串"（直到问题解决）。

**面试意义**：这解释了 Function Calling 的本质安全模型——模型没有任何系统权限，它碰不到服务器、数据库、日志，只能"提请求"。执行与否、执行什么，控制权全在应用侧（工具白名单、参数校验都做在这层）。

#### 问题 11：ReAct 范式 vs 现代 Function Calling

**认知**：ReAct（2022 Yao 论文）= Reasoning + Acting，核心是"推理和行动交替进行"。论文时代的实现是纯 prompt 约定（`Thought:/Action:/Observation:` 文本格式 + 停用词解析）。现代 Function Calling 是它的结构化工程演进版：Thought 藏进工具决策，Action 变成 `tool_calls` 结构化字段，Observation 变成带 `tool_call_id` 的 tool 消息。**范式没变，协议从"文本约定"升级成"结构化契约"**。

**面试标准答法**："我的循环结构是 ReAct 的（think→act→observe 交替、观察驱动下一轮决策），但工具调用协议用现代 Function Calling 而非论文的停用词解析——因为停用词会被推理模型的中间思维误触发提前截断，结构化契约更稳。"

### Week 3：SSE 流式与前端

#### 问题 12：并行 Edit 操作互相覆盖导致 agent.py 状态混乱

**现象**：给 `agent.py` 加 `event_hook`（SSE 事件回调），用多个 Edit 操作改同一文件，跑测试报 `AttributeError: 'Agent' object has no attribute '_emit'`。

**排查**：第一个 Edit（加 `event_hook`/`_emit` 到 `__init__`）没生效（old_string 没匹配上），但后面的 Edit 加了调用 `self._emit(...)` 的代码——方法没定义但被调用了，运行时炸。

**根因**：多个 Edit 操作在同一文件，如果它们的 old_string 有重叠或先后依赖，后面的 Edit 可能让前面的 Edit 失效，或自己匹配不到最新内容。

**解法**：放弃逐个 Edit，用 `Write` 工具重写整个 `agent.py` 一次性把所有 event_hook 逻辑写进去。

**教训**：同一文件多处改动且互相依赖时，宁可重写整文件也不要并行 Edit。Edit 是"精确替换"，适合小改；大改用 Write 一次性写完更可靠。

#### 问题 13：端口占用（开发期间反复踩）

**现象**：启动 server 报 `Address already in use`，端口 8765 被旧 server 占着。

**排查**：之前的 server 进程没正常退出，端口还在 LISTEN 状态。

**解法**：换端口（8766/8767），或用 `Get-NetTCPConnection -LocalPort <port>` 找到 PID 后 `Stop-Process`。生产环境用 systemd/守护进程管理，开发期就换端口最快。

### 收尾代码复查（Week 4）

#### 问题 14：`config.py` import 时就 raise，破坏可测试性

**现象**：跑 router mock 测试，无 key 环境下直接挂——还没到测试逻辑，import config 就抛 `RuntimeError("请先设置环境变量...")`。

**排查**：原代码：
```python
DEEPSEEK_API_KEY = os.environ.get("DEEPSEEK_API_KEY")
if not DEEPSEEK_API_KEY:
    raise RuntimeError("请先设置环境变量 DEEPSEEK_API_KEY")
```
import 时就执行 raise，导致**所有依赖 config 的测试都被真实 key 绑架**——mock 测试本该零依赖。

**解法**：改为运行时校验，提供 `require_api_key()` 函数：
```python
DEEPSEEK_API_KEY = os.environ.get("DEEPSEEK_API_KEY")  # 不 raise

def require_api_key() -> str:
    if not DEEPSEEK_API_KEY:
        raise RuntimeError("请先设置环境变量 DEEPSEEK_API_KEY")
    return DEEPSEEK_API_KEY
```
真实调用方（cli/server/eval）调 `require_api_key()`，mock 测试不调它，互不干扰。

**教训**：import 副作用破坏可测试性。模块导入应该是"纯声明"——加载常量、定义函数，但不做任何会失败的动作（连数据库、读文件、raise）。需要失败的动作放函数里，调用方决定何时触发。

#### 问题 15：`eval.py` 用正则从 cli.py 源码抽 SYSTEM_PROMPT

**现象**：`eval.py` 里这么拿 system prompt：
```python
SYSTEM_PROMPT = open(Path(__file__).parent / "cli.py", encoding="utf-8").read()
m = re.search(r'SYSTEM_PROMPT = """.*?"""', SYSTEM_PROMPT, re.DOTALL)
sp = m.group(0).split('=', 1)[1].strip().strip('"') if m else "你是运维助手。"
```
读 cli.py 的源码文本，用正则抽变量定义——脆弱 hack，cli.py 格式一改就挂。

**解法**：直接 import：
```python
from cli import SYSTEM_PROMPT as sp
```

**教训**：能 import 就别正则解析源码。Python 的 import 机制就是为复用变量/函数设计的，正则解析源码是"绕过语言机制做反射"，又脆又难维护。

#### 问题 16：`--baseline all` 跑占位基线，报告会误导

**现象**：`eval.py --baseline all` 会跑 `rag_lora` 基线，但那是占位实现（复用纯 RAG 逻辑），产出的数据和纯 RAG 完全一样。报告页看到三条柱子，第三条和第二条一模一样，会误导读者以为 LoRA 没效果。

**解法**：`--baseline all` 改为只跑 `agent` + `rag` 两基线，`rag_lora` 需显式 `--baseline rag_lora` 才跑（带占位警告）。

**教训**：占位实现要么不暴露，要么明确标注。让占位混进默认流程，等于用假数据误导读者。

#### 问题 17：`report.html` 柱状图对无数据基线渲染 0% 柱子

**现象**：报告页柱状图，没跑的基线显示 0% 柱子，看起来像"该基线得 0 分"，其实是"没跑"。

**解法**：只渲染有数据的基线，`data[bl] && data[bl].aggregate` 都为真才画柱子。

**教训**：可视化要区分"0 值"和"无数据"。0 是测出来的，无数据是没测，两者意义完全不同，渲染时要分别处理。

### 真实 API 验证暴露的设计缺陷（Week 4 收尾）

#### 问题 18：动作型查询路由误判（项目最重要的真实缺陷）

**现象**：用真实 API 跑 `verify.py` 步骤 3，第三条"查一下 nginx 最近的报错日志"被路由到 refuse_human（sim=0.29 < 0.45），但用户意图明显是"查日志"——Agent 该处理，不该拒答。

**根因分析**：路由决策完全靠 RAG 相似度。但 KB 是知识型内容（nginx 502 怎么排查、OOM 处理方法），没有"查/执行/诊断"这类动作描述。动作型查询（查日志/查监控/查进程）和 KB 语义距离远，sim 天然偏低，被误判到 refuse_human。

这不是 mock 测试能发现的——mock 用的 stub LLM 不走真实路由，sim 是预置的。只有真实 API + 真实 query 才暴露。

**修复**：router.py 加 `_detect_intent` 意图检测层：
```python
def _detect_intent(self, query: str) -> bool:
    q = query.lower()
    has_action = any(v in q for v in _ACTION_VERBS)
    has_theme = any(t in q for t in _TOOL_THEMES)
    return has_action and has_theme  # 双命中
```
逻辑：只在 `sim < sim_low`（本要 refuse_human）时才触发，不干扰高/中置信路径。命中就救回 agent_loop。

**为什么双命中而不是单命中**：单命中过激。"查一下天气"只有动作词无主题词，不该走 agent；"nginx 502 是什么"若 sim 高走 rag_direct 根本到不了意图检测层，但若 sim 低，有主题词无动作词也不该强救。双命中保证只救"明确要执行运维动作"的查询。

**v1 vs v3 真实数据对比**（20 题 × 2 基线，真实 API，v3=最终版含问题19先验注入修复）：

|---|---|---|---|

| tool_accuracy_avg | 0.450 | **1.000** | 0 |
| param_accuracy_avg | 0.450 | 0.925 | 0 |
| turns_avg | 1.200 | 3.950 | 0 |
| latency_ms_avg | 1879 | 5382 | 2193 |
| 路由分布 | 多数 refuse | 16 agent_loop / 2 refuse / 2 rag_direct | — |

#### 问题 19：RAG 先验注入没做相似度门控（真实使用暴露）

**现象**：用户问"昨晚 web-01 为什么变慢"，Agent 开头却复述"根据知识库片段 [kb-002]，处理 MySQL 'Too many connections' 错误的方法如下..."——明明问的是 web-01 变慢，答的却是 mysql 连接数处理。

**排查**：这条 query sim=0.0（KB 没相关内容），但意图检测命中（"为什么"+"变慢"双命中）救回 agent_loop。进 `_route_agent_loop` 后，第 145 行：
```python
if kb_hits:  # ← 只检查非空，不管 sim 多低
    prior = f"... {kb_hits[0]['text']}"
```
`rag_search` 即使 sim=0 也返回 top_k 个结果（按相似度排序，都不相关也返回）→ `kb_hits` 非空 → 注入了 kb-002 mysql 的先验 → LLM 被误导开头复述 mysql 处理方法。

**根因**：把"检索结果"当"相关知识"用。相似度排序 ≠ 相似度过滤。RAG 永远会返回 top_k 个结果，即使都不相关——把不相关结果注入 prompt 等于把噪声当信号，LLM 会被带偏。

**修复**：加相似度门控——只有 `sim >= sim_low` 才注入先验，否则纯走 Agent 调工具：
```python
# 修复前
if kb_hits:  # 只看非空
    prior = f"... {kb_hits[0]['text']}"

# 修复后
if kb_hits and sim >= self.sim_low:  # 门控：sim 不够不注入
    prior = f"... {kb_hits[0]['text']}"
```
同时 `kb_hits` 返回值也加门控——sim 低于阈值时返回空列表，前端溯源面板不显示无关片段。

**修复后验证**（真实 API）：13 次工具调用全对（query_log/监控 cpu/memory/disk/network/查 ERROR/OOM/timeout/free/ps/df/rag_search 验证），答案直接定位 `Out of memory: Killed process 3321 (java)` OOM 根因，开头不再复述 mysql。

**三版本数据对比**（20 题 × 2 基线，真实 API）：

| 指标 | v1 窄意图 | v2 buggy 先验 | v3 修复后 | RAG |
|---|---|---|---|---|
| answer_score_avg | 0.875 | 0.975 | **0.975** | 0.975 |
| tool_accuracy_avg | 0.450 | 1.000 | **1.000** | 0 |
| turns_avg | 1.200 | 4.850 | **3.950** ↓ | 0 |
| latency_ms_avg | 1879 | 6353 | **5382** ↓15% | 2193 |

**关键洞察**：修复不仅去除了误导（不再复述 mysql），还**提升了效率**——turns 从 4.85 降到 3.95，延迟降 15%。原因：无关先验是噪声，Agent 之前要花轮次处理/推翻它；去掉噪声后 Agent 直接调工具诊断，路径更短。这是"噪声不止误导，还增加成本"的实证。

**为什么之前没暴露**：① mock 测试 sim 是预置的，不走真实 RAG 算法；② verify.py 三条 case 恰好不撞这个场景（mysql sim=0.79 走 rag_direct、午饭 sim=0 走 refuse、查日志 sim=0.29 但 KB 碰巧有点相关）。**只有真实用户问"昨晚 web-01 为什么变慢"这种 sim=0 但意图命中的查询才暴露**——又一个"真实使用才能发现的缺陷"。

**教训（面试讲法）**：RAG 检索永远会返回 top_k 个结果，即使都不相关。相似度排序 ≠ 相似度过滤。先验注入必须做相似度门控——这是 RAG 系统的标准防御，但很容易漏，因为开发时用的测试 query 通常都和 KB 有点关系，不会撞到 sim=0 的场景。我的项目里这个 bug 藏了四周，直到真实用户问了才暴露。修复后还有意外收获：效率提升 15%——证明噪声先验不只误导，还增加 Agent 的推理成本。

### 真实数据库改造（v4 收尾：mock 常量 → ChromaDB + SQLite + Docker）

> 前 19 个问题都发生在"全 mock 数据"阶段。用户一句"那现在都是 mock 数据，需要换成真实数据加数据库呀，要不然这项目有什么用"触发了 v4 改造：知识库迁 ChromaDB、日志/监控迁 SQLite、命令诊断走 Docker 真实容器。下面三个问题是**真实数据库迁移时新踩的坑**，比前 19 个更贴近"生产化"——面试讲这个最能体现你做过真东西。

#### 问题 20：ChromaDB 相似度计算的"隐藏约定"（向量库迁移坑）

**背景**：KB 从 Python 常量 + n-gram 相似度，迁移到 ChromaDB + sentence-transformers（`paraphrase-multilingual-MiniLM-L12-v2`，384 维，cosine 距离）。

**现象（踩坑）**：ChromaDB 返回的 `distance` 含义由建库时的 `hnsw:space` 配置决定——**默认 l2 返回的是 squared L2（不是余弦）**，只有显式配 `hnsw:space=cosine` 才返回 `1 - cos_sim`。这套"隐藏约定"在文档里不显眼，第一次跑时直接把 distance 当余弦相似度用，数值完全对不上（l2 距离和余弦是两个量纲）。

**修复**（已写入 `db/init_chroma.py` + `tools/rag_search.py`）：
1. 建库显式配余弦空间：
   ```python
   collection = client.create_collection(
       name="ops_kb",
       configuration={"hnsw:space": "cosine"})  # 关键：声明 distance 语义
   ```
2. 验证时用 `sim = 1 - dist`（cosine 空间下成立）。
3. `rag_search.py` 用 numpy **手算余弦** `_cosine_similarity`（dot / 模长乘积）对 top_k 候选做精排，**不依赖 ChromaDB 返回的 distance 字段**：
   ```python
   sim = np.dot(a, b) / (np.linalg.norm(a) * np.linalg.norm(b))
   ```
   即使 ChromaDB 版本升级改了 distance 语义，Router 拿到的 sim 也稳定——把相似度计算从向量库实现里**解耦**出来。

**面试讲法**："向量库的相似度不是开箱即用的。我先确认 `hnsw:space` 配置（默认 l2 是 squared L2，不能等于余弦），再用 numpy 独立算余弦做精排。相似度这种核心信号不能绑死在某一版向量库的 distance 实现上。"

#### 问题 21：SQLite `query_logs` 时间窗口 + 匹配字段 bug（真实数据暴露）

**背景**：日志从 `MOCK_LOGS`（6 条常量）迁到 SQLite `logs` 表（552 条真实格式数据，时间跨 3 天：`2026-09-02 ~ 2026-09-04`）。

**现象（初始版本三个 bug，已修）**：
1. **时间窗口把故障数据全过滤掉**：最初用 `datetime('now', '-' || hours || ' hours')` 作基准——但预置数据时间戳是 9 月初，而当前真实时间是 9 月，窗口直接把那 3 天的历史故障日志全滤掉了，查啥都空。
2. **keyword 只匹配 message**：`LIKE '%kw%'` 只搜 `message` 字段。但用户说"查 nginx 日志"时 nginx 是 **service 不是 message**，只搜 message 会漏掉整类日志。
3. **大小写敏感**：`Nginx` 搜不到 `nginx`。

**修复**（`db/db.py` 现状，已验证）：
```python
# 1. 时间基准改成数据自身最新时间，不依赖 now()
sql = ("SELECT ... FROM logs WHERE timestamp >= "
       "(SELECT datetime(MAX(timestamp), '-' || ? || ' hours') FROM logs)")
# 2. keyword 同时匹配 service + message，大小写不敏感
kw = f"%{keyword.lower()}%"
sql += " AND (LOWER(service) LIKE ? OR LOWER(message) LIKE ?)"
# 3. 排序 ERROR/WARN 优先（CASE 权重），同级时间倒序
sql += " ORDER BY CASE level WHEN 'ERROR' THEN 0 WHEN 'WARN' THEN 1 ELSE 2 END, timestamp DESC"
```

**面试讲法**："预置数据时间戳和真实当前时间错位，用 `now()` 当基准会把历史故障数据全滤掉——正确做法是用数据自身的最新时间做基准。另外日志检索要同时匹配 service 和 message，因为用户口中的服务名在 service 字段不在 message。这两个坑都只有'真实数据 + 真实查询'才暴露，mock 6 条常量根本测不出来。"

#### 问题 22：迁移后三套测试套件全挂（依赖与断言失配）

**现象**：工具从 mock 换成真实 DB 后，三个测试套件 import/运行全挂——不是逻辑错，是**测试本身没跟着实现演进**。

**根因与修复**：
1. **agent mock 测试断言条数失效**：`query_log` 工具现在查 SQLite 的 552 条真实数据，一条 `keyword='mysql'` 命中多条。原断言 `len(result) == 1`（基于 6 条 mock 常量）必然失败。修复：断言改为"结果非空且含关键词"，**不再假定条数**：
   ```python
   assert check("v1 结果非空且含 mysql 日志",
                step["result"] and "mysql" in step["result"])
   ```
2. **router mock 测试中置信用例失效**：原本用 `"nginx 502 bad gateway 怎么排查"` 期望落中置信区间 `[0.45, 0.70)`。但向量检索后 sim 值和 n-gram 完全不同——这条 query 向量 sim≈0.83 直接走 `rag_direct`，根本到不了 `agent_loop` 分支。修复：中置信用例换成 `"nginx 报错了"`（向量 sim 落在 `[0.45, 0.70)` 区间），docstring 标注"向量检索后 sim 值和 n-gram 不同"：
   ```python
   # 向量检索后 sim 值和 n-gram 不同，用'nginx 报错了'触发中置信区间。
   result = router.route("nginx 报错了")
   assert check("agent_loop sim 在中区间 [0.45, 0.70)", 0.45 <= result.sim < 0.70)
   ```
3. **运行环境依赖**：测试依赖 ChromaDB（`rag_search` 工具）+ SQLite（`ops.db`），需先在 venv（装了 `chromadb`/`sentence-transformers`）里 `python db/init_db.py` + `python db/init_chroma.py` 初始化。用裸 python 跑会因缺 `chromadb` 直接 import 失败。

**额外发现（文档陷阱）**：测试文件 docstring 里写的 `"mysql too many connections" → sim=0.792` 是迁移前的旧值；真实 ChromaDB 跑出来是 **sim=0.834**（`eval_report.json` Q01 可证）。**sim 值随 embedding 模型/向量库变化，不能把数值写死在注释里当真理——测试应断言路由分支/区间，而非精确 sim。**

**面试讲法**："mock 到真实数据的迁移不是改个实现就行，测试也得跟着演进：断言要从'假定条数'改成'断言行为'，预期 sim 要从 n-gram 经验值改成向量检索实测区间。这也是'测试和实现一起演进'的实例——测试不跟着实现走，迁移后就是一片红。"

## 二、测试体系

### 设计原则：分层测试，逐层逼近真实

| 层 | 工具 | 消耗 | 验证什么 |
|---|---|---|---|
| L0 单元逻辑 | `tests/test_eval_logic.py` | 零 | 评分函数（关键词命中/路由标签正确性） |
| L1 mock 主循环 | `tests/test_agent_mock.py` | 零 | Agent 五场景（单工具/多工具/JSON解析失败/异常回传/max_turns 兜底） |
| L2 mock 路由 | `tests/test_router_mock.py` | 零 | 三分支路由（rag_direct/agent_loop/refuse_human）+ LLM 调用次数 |
| L3 一键自检 | `verify.py` | 步骤3 约3次调用（几分钱） | 全链路：测试套件 → key 加载 → 真实对话三路由 |
| L4 三基线评估 | `eval.py` | 20题×2基线（约¥5） | answer_score/tool_accuracy/param_accuracy/turns/latency 五指标 |

### mock 测试怎么写的（面试可讲）

**核心技巧**：用 `StubLLM`（按剧本出牌的假 LLM）驱动真实 Agent，验证主循环全分支，零 API 消耗。

```python
class StubLLM:
    """按预设剧本返回 tool_calls，验证 Agent 主循环逻辑。"""
    def __init__(self, script):  # script 是预设的 response 列表
        self.script = script
        self.idx = 0
    def chat(self, messages, tools=None, stream=False):
        resp = self.script[self.idx]
        self.idx += 1
        return resp  # 返回构造好的 make_response(tool_calls=...)
```

**五个场景覆盖**（test_agent_mock.py）：
- v1：单工具单轮（问天气 → 调天气工具 → 答案）
- v2：多工具并行（模型一轮声明两个 tool_calls，都要配对 tool 消息）
- v3：JSON 解析失败防御（模型返回的 arguments 是坏 JSON，call 要捕获异常回传错误而非崩溃）
- v4：工具执行异常回传（call 抛异常，Agent 要 catch 并把错误信息作为 observation 回填）
- v5：max_turns 兜底（循环到上限还没结束，强制不带 tools 再调一次让模型总结）

**为什么 mock 测试有价值**：① 零成本可反复跑；② 验证的是"我的循环逻辑"而非"模型能力"——模型能力是黑盒，循环逻辑是白盒，白盒才该被测试覆盖；③ 修复意图检测后，mock 测试全过，证明改动没破坏现有逻辑，再上真实 API。

### 真实 API 验证流程

**verify.py 三步**：
1. 跑三个 mock 测试套件（零消耗）——全过才继续
2. 检查 `.env` 或环境变量有没有 key——没有就停在步骤 1，报告"代码逻辑健康，真实链路待 key"
3. 真实对话三路由验证（约 3 次 LLM 调用）：
   - `mysql too many connections 怎么办` → 期望 rag_direct（知识型，KB 直答）
   - `今天午饭吃什么` → 期望 refuse_human（超纲，拒答转人工）
   - `查一下 nginx 最近的报错日志` → 期望 agent_loop（动作型，调工具）

**关键认知**：mock 测试发现不了"动作型查询路由误判"——因为 mock 的 sim 是预置的，不走真实 RAG 算法。只有真实 API + 真实 query 才暴露。这就是分层测试的局限：每一层只覆盖自己那层的问题，真实链路有真实链路才能发现的缺陷。

### eval.py 三基线评估

**测试集**：`data/eval_questions.jsonl`，20 条运维问题，分四类：
- 知识型（Q01-Q06）：nginx 502 排查/OOM 处理/mysql 连接数——KB 有，走 rag_direct
- 动作型（Q08-Q14, Q18-Q20）：查 cpu/查磁盘/看进程——Agent 该调工具
- 超纲（Q07, Q10）：你好/午饭——该拒答
- 复合型（Q02, Q09, Q17）：既要知识又要查实时数据——Agent 调工具 + KB 先验

**五指标**：
- `answer_score`：答案正确性（关键词命中 + 路由标签正确性，0/0.5/1 三档）
- `tool_accuracy`：是否调对了工具（Agent 基线才有，RAG 恒 0）

## 三、关键设计决策与权衡

### 决策 1：先手写循环再用框架

**选择**：agent.py 主循环手写 ReAct while 循环，不直接用 LangChain/LangGraph。

**理由**：面试被问"你的 Agent 循环怎么实现的"时，能手指出每一行——`tool_calls` 解析、`tool_call_id` 配对、max_turns 兜底——而不是说"我调了 LangChain 的 AgentExecutor"。框架是生产力工具，但面试要的是原理理解。

### 决策 2：RAG 工具双重身份

**选择**：`rag_search` 既是 Router 的信号源（直接调拿 sim 分数），又是 Agent 工具池一员（LLM 可调）。

**理由**：两次调用目的不同——第一次是"要不要进循环"的信号，第二次是"循环里要不要查知识"的选项。这样设计避免 Router 和 Agent 各维护一套检索逻辑，单一数据源。

### 决策 3：命令诊断白名单沙箱

**选择**：`diagnose` 工具只允许执行预定义白名单命令（ps/free/df/netstat），不接受任意命令。

**理由**：Function Calling 的安全模型——模型只提请求，执行控制权在应用侧。白名单是"即使模型生成恶意命令，应用侧也不执行"的兜底。面试讲"你怎么防注入"就这么答。

### 决策 4：event_hook 事件流（SSE 基础）

**选择**：Agent 和 Router 加 `event_hook` 回调，不传时退化为同步，传了就实时推送中间状态。

**理由**：SSE 流式需要实时推送 `route/tool_call/tool_result/answer` 事件。用 event_hook 解耦——业务逻辑不关心是否流式，流式是"外挂"的关注点。这样 mock 测试不传 hook 就是同步，生产传 hook 就是流式，同一套逻辑。

### 决策 5：意图检测只在低置信触发（不干扰高/中置信）

**选择**：`_detect_intent` 只在 `sim < sim_low`（本要 refuse_human）时才触发。

**理由**：如果让意图检测对高置信也生效，会发生坏事——用户问"mysql too many connections 怎么办"（KB 有，sim 0.79），本该 rag_direct 快答，意图检测却因为"怎么办"是动作词把它救去走 agent_loop，多花约 3 倍延迟还可能调错工具。意图检测是"拒答的逃生通道"，不是"所有路径的 override"。

### 决策 6：LoRA 基线占位

**选择**：`rag_lora` 基线目前复用纯 RAG 逻辑（占位），接真实 Qwen2.5-1.5B+LoRA 时替换 `lora_llm`。

**理由**：本地 CPU-only 跑 1.5B 推理太慢（单题 30s+），不适合做 20 题评估。先占位保证评估框架完整，真实 LoRA 数据后续补。`--baseline all` 默认不跑它，避免占位数据污染报告。

## 四、面试过程叙事模板

### 3 分钟项目讲法（时间轴版）

> 我做了一个企业 IT 运维智能体（Ops Agent）。技术栈是 DeepSeek API + 手写 ReAct 循环 + FastAPI SSE + 原生 HTML 前端。
>
> **开发过程**分四周：第一周手写 Agent 核心循环——LLM 客户端封装、工具注册表（用装饰器 + 全局字典）、`to_openai_schema` 参数格式转换、ReAct 主循环（最大轮次 + 三层防御）。这周踩了循环导入、抽象类实例化、required 在循环里被覆盖三个 Python 机制坑，全是面试常问的。
>
> 第二周做决策路由——把 RAG 检索置信度（三级阈值 sim_high=0.70/sim_low=0.45/kw_coverage_low=0.3）改造成路由模块，高置信走 RAG 直答、中置信走 Agent 循环、低置信拒答转人工。还实现了 4 个运维工具：日志查询、监控查询、命令诊断（白名单沙箱）、RAG 检索（双重身份）。
>
> 第三周做 SSE 流式 + Web 界面——FastAPI 后端 token 级流式输出，前端四个 P0 功能：流式对话窗、Agent 执行时间线、决策路由徽章、RAG 引用溯源面板。
>
> 第四周做评估——20 条测试集三基线框架对比（纯 RAG / RAG+LoRA 预留 / Agent），五指标（answer_score/tool_accuracy/param_accuracy/turns/latency）。
>
> **最有价值的一个发现**：跑真实 API 评估时，我发现一个设计缺陷——路由完全靠 RAG 相似度，但 KB 是知识型内容，对"查日志/查监控"这类动作型查询打分偏低（sim 0.29 < 0.45），被误判到拒答。我加了意图检测层（动作词+主题词双命中），只在低置信时触发兜底。修复后 agent answer 从 0.875 反超到 0.975，tool_accuracy 从 0.45 到 1.000，代价是约 2.9 倍延迟——这是准确率/延迟权衡的经典案例。后续修先验注入 bug 还把延迟从 6353 降到 5382（问题19），证明噪声先验不只误导还增加推理成本。

### 关键问答速查

| 面试官问 | 你的答（简短版） |
|---|---|
| 你的 Agent 循环怎么实现的？ | ReAct while 循环：模型返回 tool_calls → 我解析 name+arguments → 调 `TOOL_REGISTRY[name].call(params)` → 结果作为 tool 消息回填（带 tool_call_id 配对）→ 再问模型。出口是模型不再返回 tool_calls；兜底是 max_turns 到顶强制不带 tools 总结。 |
| 模型执行了函数吗？ | 没有。模型只输出"我要调 query_log，参数 {...}"这段结构化文本。执行、回填、循环控制全在我写的 Python 代码里。这就是 Function Calling 的安全模型——模型只提请求，控制权在应用侧。 |
| ReAct 和 Function Calling 什么关系？ | ReAct 是范式（think→act→observe 交替），Function Calling 是协议。我的循环是 ReAct 结构，但用现代 Function Calling（结构化 tool_calls）而非论文的停用词文本解析——停用词会被推理模型中间思维误触发。 |
| 循环导入怎么解决？ | 三种：底部 import（我用的）、函数内延迟 import、重新设计模块职责。我选底部 import 因为职责清晰，只是初始化顺序问题。 |
| 装饰器什么时候执行？ | 类定义代码被执行时——也就是模块被 import 时。模块没被 import，`@register_tool` 一行都不跑，注册表就是空的。 |
| required 为什么会丢？ | 循环里直接赋值 `=` 是覆盖不是累加。改用列表推导移出循环 `[p["name"] for p in params if p.get("required")]`，既解决覆盖又更 Pythonic。 |
| 路由为什么不能只靠 RAG 相似度？ | KB 是知识型内容，对动作型查询（查日志/查监控）打分偏低，会误判到拒答。我加意图检测兜底，但只在低置信触发——高置信走 RAG 直答最快，不能让意图检测把快路径拖慢。 |
| 延迟怎么优化？ | 三个方向：并行 tool_calls（模型一轮可声明多个，现在串行执行）、工具结果缓存（同 query 短期复用）、分级 SLA（知识型快答/动作型慢答，SSE 流式让用户感知"在干活"而非"在等"）。我项目里②③做了，①是下一步。另外问题19先验注入门控修复意外降了 15% 延迟（噪声先验会让 Agent 多花轮次处理）。 |
| 怎么防模型执行恶意命令？ | 命令诊断工具用白名单——只接受 ps/free/df/netstat 预定义命令，模型生成的命令不在白名单就拒绝。模型只提请求，执行与否应用侧说了算。 |
| 测试怎么做的？ | 分层：mock 测试（StubLLM 按剧本出牌，零 API 消耗，验证主循环五场景）→ verify.py 一键自检（真实对话三路由）→ eval.py 三基线评估（20题×2基线五指标）。mock 发现不了路由误判，真实 API 才暴露——这是分层测试的局限。 |
| 为什么手写循环不用 LangChain？ | 面试要的是原理理解。手写能指出每一行——tool_call_id 配对、max_turns 兜底、异常回传。框架是生产力工具，但被问"循环怎么实现"时答"我调了 AgentExecutor"是减分的。 |
