## 一、项目概述

### 1.1 项目定位

Ops Agent 是一个面向企业 IT 运维场景的智能体应用，能根据用户问题的语义特征**自动分流**到三条处理路径——知识库直答、Agent 工具循环、拒答转人工——并在 Agent 路径中通过 ReAct 循环多轮调用运维工具（查日志 / 查监控 / 执行诊断命令 / 检索知识库）完成故障定位。

### 1.2 业务背景

项目源自企业 IT 运维 QA 助手的真实场景：一线工程师每天面对大量"nginx 为什么 502""mysql 连接数打满怎么办""昨晚某台机器为什么变慢"的问题。传统做法是查文档 + 登机器看日志 + 看监控，一个故障排查可能横跨多个系统。Ops Agent 把这套流程自动化：用户用自然语言提问，Agent 自动决定是查知识库还是调工具，多轮收集证据后给出带依据的诊断结论。

### 1.3 技术架构与开发迭代（面试核心故事线）

本项目是一个从零构建的运维智能体（Ops Agent），内部采用 **RAG（知识检索 + 置信度信号）+ Agent（编排 + 工具调用）** 混合架构。开发上迭代经历了「窄意图 RAG → RAG 路由 → Agent 循环」三个阶段，每一阶段都有真实数据和工程权衡支撑（详见 9.4）；LoRA 微调是我单独完成的另一条验证线，未接入本项目运行链路（见 14.1 局限）。

| 阶段 | 方案 | 能力边界 | 备注 |
|---|---|---|---|
| 纯 RAG（向量检索 + 生成） | 只能答知识库已有的问题 | 用户问"查 nginx 日志"——KB 里没有动作型查询，答不了 | 本项目 RAG 检索同时作为路由信号源 |
| 本地 Qwen2.5-1.5B+LoRA 微调 | 答案更贴合运维语境 | 微调只能改语言风格，学不会"执行" | **独立验证线，未接入本项目运行链路** |
| **Agent（Router + ReAct 循环 + 工具）（本项目）** | **能调工具查实时数据，能拒答转人工** | 真实运维需要"行动"不只是"回答" | 交付主体 |

三基线评估框架（纯 RAG / RAG+LoRA / Agent）中，本项目已跑真实数据的是 `rag` 与 `agent` 两条；`rag_lora` 为设计预留基线（见 9.1 / 14.1）。

## 二、技术选型

### 2.1 选型总览

| 层 | 选型 | 备选 | 选择理由 |
|---|---|---|---|
| LLM | DeepSeek API（deepseek-chat） | Qwen API / 本地 Qwen2.5-1.5B+LoRA | OpenAI 兼容接口、成本低（全项目评估 < ¥10）、CPU-only 环境可跑 |
| LLM 客户端 | openai SDK（Python） | langchain / 自写 HTTP | 只用 chat.completions.create 一个端点，SDK 足够；不引框架便于讲清原理 |
| Agent 循环 | **手写 ReAct 循环** | LangChain Agent / Qwen-Agent 框架 | 面试要能讲清循环每一步；框架藏细节，被追问答不出本质 |
| 工具调用协议 | OpenAI Function Calling | ReAct 停用词文本解析 | 结构化契约比文本约定稳；推理模型的中间思维可能撞停用词导致提前截断 |
| Web 框架 | FastAPI | Flask / Gradio | 原生支持 StreamingResponse（SSE）；Gradio 做不了自定义时间线和路由徽章 |
| 流式协议 | SSE（Server-Sent Events） | WebSocket | 单向推送场景，SSE 比 WS 轻；浏览器原生 EventSource，无需额外库 |
| 前端 | 原生 HTML + JS（单页） | Gradio / Streamlit / React | 4 个 P0 可视化（时间线/徽章/溯源/统计）自定义度高，原生最直接 |
| 部署 | Docker（python:3.11-slim） | 裸机 / k8s | 单容器够用；Dockerfile 标准模板，面试演示可一键构建 |
| 测试 | unittest 风格 + mock LLM | pytest | 零依赖，聚焦"用假 LLM 驱动真实 Agent"验证循环逻辑 |

### 2.2 关键选型决策

**决策 1：手写 Agent 循环而不用 LangChain**

- 选了什么：自己写 `while` 循环 + `tool_calls` 解析 + `tool_call_id` 配对
- 为什么：LangChain 的 `AgentExecutor` 把循环、工具分发、记忆管理全包了，被面试官问"你的 Agent 循环怎么实现的"只能答"我调了 LangChain"——这等于没做
- 不这么选会怎样：开发快 3 倍，但讲不清 `tool_call_id` 为什么必须配对、max_turns 兜底怎么处理、并行 tool_calls 怎么遍历，面试直接挂

**决策 2：LLM 走 API 而非本地推理**

- 选了什么：DeepSeek API 作为主 LLM；本地 Qwen2.5-1.5B+LoRA 是考虑过的备选，但本机 CPU-only 单题 30s+，且本项目最终以 API 为主，本地 LoRA 仅作为设计预留的评估基线（`rag_lora`），未接入运行链路
- 为什么：开发机 CPU-only，本地推理单题 30s+，开发节奏扛不住；API 单题 2-5s，全项目评估成本 < ¥10
- 不这么选会怎样：能讲"全栈本地化"但开发周期翻 5 倍，且 CPU 推理延迟会让 SSE 流式演示失去意义

**决策 3：RAG 工具双重身份**

- 选了什么：`rag_search` 既是 Router 的决策信号源（直接调拿 sim 分数），又是 Agent 工具池的一员（LLM 可调它查知识）
- 为什么：Router 需要相似度做路由决策，Agent 需要知识片段做先验——两次需求指向同一个检索能力，合并成一个工具避免重复检索
- 不这么选会怎样：Router 内部写一套检索逻辑、Agent 工具池再放一个检索工具，代码重复且两次检索结果可能不一致

## 四、数据来源与构建

本项目使用 **ChromaDB 向量库 + SQLite 关系库** 真实存储数据，所有数据通过初始化脚本生成（`db/init_db.py` + `db/init_chroma.py`），clone 后跑初始化即可。工具接口设计成"换实现不改接口"——生产化时把 ChromaDB/SQLite 换成 Qdrant/Prometheus/ELK，`call` 返回结构不变。

### 4.1 知识库（ChromaDB 向量库，15 条 KB）

**来源**：基于酷哇科技实训期间企业 IT 运维 QA 助手项目沉淀的高频问题，提炼出 4 条核心知识片段。

**构建方法**：每条 KB 是一个 dict，含四个字段：

| 字段 | 作用 | 示例 |
|---|---|---|
| `id` | 唯一标识，答案里引用片段编号用 | `"kb-001"` |
| `text` | 知识正文，排查步骤或处理方法 | "nginx 502 Bad Gateway 错误通常由上游服务无响应..." |
| `keywords` | 关键词列表，用于 `_kw_coverage` 计算 | `["nginx", "502", "bad gateway", "上游", "超时"]` |

**4 条 KB 覆盖的故障模式**：

| KB ID | 故障类型 | 设计意图 |
|---|---|---|
| kb-001 | nginx 502 Bad Gateway | 上游服务无响应/超时的排查步骤 |
| kb-002 | mysql Too many connections | 连接数耗尽的处理方法 |
| kb-003 | Linux OOM Killer | 内存耗尽杀进程的定位 |
| kb-004 | 磁盘空间不足 | 磁盘满的排查步骤 |

**为什么是 4 条不是 400 条**：这是面试演示项目，4 条足以覆盖三条路由分支（知识型 / 动作型 / 超纲）。生产化时换成真实向量库（如 Qdrant / Milvus），接口不变。

### 4.2 运维日志库（SQLite logs 表，552 条）

**来源**：设计了一个**故障链故事**——web-01 主机昨晚发生的一系列连锁故障，6 条日志按时间排序：

| 时间 | 级别 | 内容 | 故事角色 |
|---|---|---|---|
| 23:12:01 | ERROR | nginx: upstream timed out... 10.0.2.15:8080 | nginx 上游超时（现象） |
| 23:12:03 | ERROR | nginx: upstream server temporarily disabled | nginx 暂时禁用上游 |
| 23:15:47 | WARN | mysql: too many connections (max=151) | mysql 连接耗尽（中间环节） |
| 23:20:11 | ERROR | kernel: Out of memory: Killed process 3321 (java) | **OOM 杀 java 进程（根因）** |
| 23:31:05 | WARN | disk: /var/lib/docker usage 92% | 磁盘告警（加重因素） |
| 23:40:22 | INFO | redis: connection reset by peer | redis 连接重置（次要现象） |

**设计意图**：这 6 条日志能串成一条完整的因果链——mysql 连接耗尽 → java 应用 OOM 被杀 → nginx 上游超时 → 磁盘快满加剧。面试演示时问"昨晚 web-01 为什么变慢"，Agent 多轮查日志 + 查监控 + 查进程，能拼出完整诊断，这是 demo 的核心戏。

### 4.3 监控指标（SQLite metrics 表，9075 条时序数据）

**来源**：与日志库的故障链呼应，预置 web-01/web-02/db-01 三台主机的四类指标。

| 指标类型 | 预置数据要点 |
|---|---|
| cpu | web-01: 92%/load 8.4（异常）；web-02: 35%（正常）；db-01: 78% |
| memory | web-01: 7.2/8G + oom_kills_24h=3（异常）；其他正常 |
| disk | web-01: /var/lib/docker 92%（异常）；其他正常 |
| network | web-01: retransmits=142（异常）；web-02: 2（正常） |

**设计意图**：监控数据和日志互相印证——日志说"OOM Killed process 3321 (java)"，监控说"memory used 7.2/8G + oom_kills_24h=3"，Agent 交叉引用就能确认根因。这是 ReAct 循环"Observation 修正下一轮 Thought"的体现。

### 4.4 命令白名单（diagnose.py 的 ALLOWED_COMMANDS）

**来源**：运维排查高频命令，6 个白名单：

| 命令 | mock 输出要点 | 排查场景 |
|---|---|---|
| `ps` | java 进程 PID 3321 CPU 92% 内存 45% | 定位资源大户 |
| `netstat` | 880 条 TIME_WAIT 连接 | 连接泄漏 |
| `df` | /var/lib/docker 92% | 磁盘满 |
| `free` | 可用 0.3G 接近 OOM | 内存紧张 |
| `systemctl status nginx` | active running + upstream timed out | 服务状态 |
| `systemctl status mysql` | active running + Too many connections | 服务状态 |

**为什么用白名单而不是真执行**：这是面试可讲的**安全设计**——模型生成的命令不可信，必须在白名单内校验后才能执行。对应 Function Calling 的安全模型：模型只能"提请求"，执行与否、执行什么，控制权全在应用侧。

### 4.5 评估测试集（data/eval_questions.jsonl）

**来源**：手写 20 条运维问题，覆盖三类查询分布。

**构建原则**：每条含 `qid` / `question` / `expected_points`（答案应命中的要点）/ `expected_tools`（期望调用的工具及参数）。

**20 条的分布**：

| 类型 | 数量 | 示例 | 期望路由 |
|---|---|---|---|
| 知识型（KB 有答案） | 5 | "mysql too many connections 怎么办" | rag_direct |
| 动作型（需调工具） | 11 | "查一下 nginx 最近的报错日志" | agent_loop |
| 状态型（查监控/命令） | 3 | "web-01 的 cpu 使用率多少" | agent_loop |
| 超纲（KB + 工具都管不了） | 1 | "今天午饭吃什么" | refuse_human |

**expected_tools 的设计**：动作型问题标注期望工具和参数，用于评估"工具选择准确率"和"参数生成准确率"。如 Q09 "查一下 nginx 最近的报错日志" 标注 `{"name": "query_log", "params": {"keyword": "nginx"}}`。

### 4.6 数据库架构（v4 真实化改造）

本项目使用 **ChromaDB（向量库）+ SQLite（关系库）** 双数据库架构：

| 数据 | 数据库 | 表/Collection | 数据量 | 初始化命令 |
|---|---|---|---|---|
| 知识库 | ChromaDB | ops_kb collection | 15 条（384 维向量） | `python db/init_chroma.py` |
| 运维日志 | SQLite | logs 表 | 552 条（3 天） | `python db/init_db.py` |
| 监控指标 | SQLite | metrics 表 | 9075 条（3 天×10min） | `python db/init_db.py` |
| 会话记忆 | SQLite | sessions 表 | 动态增长 | 自动建表 |
| 评估报告 | JSON 文件 | reports/eval_report.json | 20 题×2 基线 | `python eval.py --baseline all` |

**ChromaDB 配置**：
- 持久化路径：`data/chroma/`（本地文件，重启不丢）
- 距离度量：cosine（余弦距离）
- embedding 模型：`paraphrase-multilingual-MiniLM-L12-v2`（384 维，多语言含中文，~100MB）
- 相似度计算：手动算余弦相似度（ChromaDB distance 是 squared L2，不直接用）

**SQLite 表结构**：
```sql
logs    (id, timestamp, level, service, host, message)          -- 索引: ts/service/level
metrics  (id, timestamp, host, metric_type, metric_name, value) -- 索引: host/type
sessions (id, session_id, role, content, created_at)            -- 索引: session_id
```

**设计保证**：所有工具的 `call(params)` 接口固定，换实现时只改内部逻辑，不改接口。如 `rag_search` 从 n-gram 改成 ChromaDB 向量检索时，`call` 返回结构不变，Router 和 Agent 无感知。生产化换 Qdrant/Prometheus/ELK 时同理。

**日志查询设计**：
- keyword 同时匹配 `service` 和 `message` 字段（用户说"查 nginx 日志"时，nginx 是服务名不是消息内容，只搜 message 会漏）
- 大小写不敏感（`LOWER()` 处理）
- ERROR/WARN 优先排序（`CASE level WHEN 'ERROR' THEN 0 ...`）
- 时间窗口基于 `MAX(timestamp)` 回溯（预置数据时间窗口和真实当前时间可能错位）

**Docker 容器命令执行**：
- 诊断命令在独立容器 `ops-diagnose-sandbox`（alpine + procps/util-linux）里真实执行
- 容器首次调用时自动构建+启动，后续 `docker exec` 执行
- 白名单校验保留（安全设计），命令在容器内真实运行而非 mock

### 4.7 数据生成方法

**日志生成**（`db/init_db.py` 的 `gen_logs`）：
- 围绕"web-01 昨晚变慢"的故障链故事，6 条核心故障日志（固定，保证 demo 效果）
- + 随机生成 3 天的正常背景日志（nginx/mysql/redis/java 服务，INFO/WARN/ERROR 按概率分布）
- + 偶发 WARN/ERROR 散落在正常时段（让 keyword 查询有结果）
- 按服务导出成真实格式日志文件（nginx_error.log / mysql_error.log / syslog.log）

**监控指标生成**（`db/init_db.py` 的 `gen_metrics`）：
- 3 台主机（web-01/web-02/db-01）× 4 类指标（cpu/memory/disk/network）× 3 天每 10 分钟一个点
- web-01 在 2026-09-04 23:00 附近 CPU/内存异常峰值（与日志故障链呼应）
- + 故障时段特殊指标（oom_kills_24h=3）

## 五、决策路由工作流

### 5.1 路由决策流程

```
用户问题
    │
    ▼
① RAG 检索（rag_search.call）
    │  返回 best_sim / best_kw_coverage / results
    ▼
② 阈值决策
    │
    ├── sim >= 0.70 且 kw_coverage >= 0.30
    │       → rag_direct（高置信，KB 直答）
    │
    ├── 0.45 <= sim < 0.70
    │       → agent_loop（中置信，走 Agent 循环）
    │
    └── sim < 0.45
            │
            ▼
        ③ 意图检测（_detect_intent）
            │  动作词 + 主题词 双命中？
            │
            ├── 是 → agent_loop（救回，reason=intent_override）
            │
            └── 否 → refuse_human（拒答转人工）
```

### 5.2 三条路径详解

**路径 1：rag_direct（高置信直答）**

- 触发条件：`sim >= 0.70 且 kw_coverage >= 0.30`
- 行为：把命中的 KB 片段交给 LLM 组织成自然语言答案，**不进 Agent 循环**
- LLM 调用次数：1 次（仅组织语言）
- 典型场景："mysql too many connections 怎么办"（sim=0.792）
- 设计意图：KB 已有完整答案时，再走 Agent 循环是浪费——直答快 3 倍

**路径 2：agent_loop（中置信走 Agent）**

- 触发条件：`0.45 <= sim < 0.70` 或 意图检测救回
- 行为：启动 ReAct 循环，LLM 多轮调工具收集证据
- 先验注入门控：`sim >= sim_low` 才把 KB 片段作为先验塞进 Agent 上下文；sim 低于阈值（意图检测救回的查询）纯走 Agent 调工具，不注入先验
- LLM 调用次数：1~8 次（max_turns 兜底）
- 典型场景："昨晚 web-01 为什么变慢"（sim=0.0，意图检测救回）
- 设计意图：信息不足时需要调工具补充实时数据

**路径 3：refuse_human（拒答转人工）**

- 触发条件：`sim < 0.45 且 意图检测不命中`
- 行为：返回拒答文案，**不调 LLM**
- LLM 调用次数：0 次
- 典型场景："今天午饭吃什么"（sim=0.0，无动作词+主题词）
- 设计意图：超出知识库范围的问题强行答会幻觉，不如拒答转人工

### 5.3 阈值体系

| 阈值 | 值 | 含义 | 来源 |
|---|---|---|---|
| SIM_HIGH | 0.70 | 高置信下限，>= 此值走 rag_direct | 沿用原 RAG 项目调参结果 |
| SIM_LOW | 0.45 | 低置信上限，< 此值走 refuse_human | 沿用原 RAG 项目调参结果 |
| KW_COVERAGE_LOW | 0.30 | 关键词覆盖率下限，与 sim 联合判定高置信 | 沿用原 RAG 项目调参结果 |

**联合判定逻辑**：高置信要求 `sim >= SIM_HIGH 且 kw_coverage >= KW_COVERAGE_LOW`——两个信号都达标才算高置信，避免单一信号误判（如 sim 高但关键词没命中，可能是巧合的字符重叠）。

### 5.4 意图检测层（router.py `_detect_intent`）

**设计动机**：真实 API 验证时发现的设计缺陷——路由完全靠 RAG 相似度，但 KB 是知识型内容（nginx 502 怎么排查 / OOM 处理），没有"查/执行"这类动作描述。动作型查询（"查 nginx 日志""查 web-01 的 cpu"）和 KB 语义距离远，sim 天然偏低（0.0~0.3），被误判到 refuse_human。

**修复方案**：加意图检测层，"动作词 + 主题词"双命中兜底。

```python
_ACTION_VERBS = {"查", "查询", "排查", "诊断", "怎么办", "为什么", "变慢", ...}
_TOOL_THEMES = {"日志", "监控", "cpu", "内存", "mysql", "nginx", "web", ...}

def _detect_intent(query):
    has_action = any(v in query.lower() for v in _ACTION_VERBS)
    has_theme = any(t in query.lower() for t in _TOOL_THEMES)
    return has_action and has_theme
```

**为什么用双命中而不是单命中**：

- 单命中过激："查一下天气"只有动作词无主题词，不该走 agent_loop
- "nginx 502 是什么"若 sim 高走 rag_direct，根本到不了意图检测层；若 sim 低，有主题词无动作词（"是什么"算问句不算动作）也不该强救
- 双命中（动作+主题）保证只救"明确要执行运维动作"的查询，是精度/召回的折中

**只在 sim < sim_low 时触发**：不干扰高/中置信路径。如果让意图检测对高置信也生效，"mysql too many connections 怎么办"（KB 有，sim=0.79）本该 rag_direct 快答，意图检测却因为"怎么办"是动作词把它救去走 agent_loop，多花约 3 倍延迟还可能调错工具。意图检测是"拒答的逃生通道"，不是"所有路径的 override"。

### 5.5 先验注入门控（问题 19 修复）

**设计缺陷**（v2 版本）：`_route_agent_loop` 的 `if kb_hits:` 只检查非空不看 sim。RAG 检索永远返回 top_k 结果即使都不相关（相似度排序 ≠ 相似度过滤），导致 sim=0 的查询被注入了无关的 KB 片段，LLM 被误导。

**典型 case**：问"昨晚 web-01 为什么变慢"（sim=0.0），KB 没有"变慢"相关内容，但 rag_search 仍返回 top_k 结果（kb-002 mysql），意图检测救回 agent_loop 后注入了 mysql 先验 → LLM 开头复述 mysql 处理方法而非直接调工具诊断。

**修复**：加相似度门控

```python
# 修复前：只看非空
if kb_hits:
    prior = f"... {kb_hits[0]['text']}"

# 修复后：sim 不够不注入
if kb_hits and sim >= self.sim_low:
    prior = f"... {kb_hits[0]['text']}"
```

**修复后效果**（v3 真实数据）：

| 指标 | v2（buggy 先验） | v3（门控修复） | 变化 |
|---|---|---|---|
| answer_score | 0.975 | 0.975 | 持平 |
| tool_accuracy | 1.000 | 1.000 | 持平 |
| turns_avg | 4.850 | 3.950 | **↓ 18%** |
| latency_ms | 6353 | 5382 | **↓ 15%** |

**意外收获**：修复不只去掉误导，还提效 15%——无关先验是噪声，Agent 之前要花轮次处理/推翻它；去掉噪声后直接调工具诊断，路径更短。"噪声不止误导，还增加成本"的实证。

## 六、Agent 循环工作流

### 6.1 ReAct 循环结构

```
用户问题 + 系统 prompt + history
    │
    ▼
┌─→ ② llm.chat(messages, tools=schemas)
│       │
│       ▼
│   ③ 模型输出 message
│       │
│       ├── 无 tool_calls → 出口：return AgentResult(answer, tool_trace)
│       │
│       └── 有 tool_calls → ⑥ 前半：assistant 消息回填（含 tool_calls 声明）
│                           │
│                           ▼
│                       遍历 tool_calls（可能多个）
│                           │
│                           ▼
│                       ④ _execute_tool(tc)
│                       │  三层防御：JSON 解析 → 工具白名单 → 执行异常
│                       │  ↓
│                       │  tool.call(params) → result (str)
│                       │
│                       ▼
│                       ⑥ 后半：tool 消息回填（tool_call_id 配对）
│                       │
└───────────────────────┘ 下一轮
    │
    ▼ （max_turns 兜底）
不带 tools 再调一次，强制基于已有信息总结
```

### 6.2 三层防御链（agent.py `_execute_tool`）

模型生成的 tool_calls 不可信，必须三层防御：

| 层 | 防御对象 | 失败处理 | 代码位置 |
|---|---|---|---|
| 1 | `arguments` 不是合法 JSON | 返回 `{"error": "参数不是合法 JSON"}` | `json.loads` try/except |
| 2 | 工具名不在注册表（模型幻觉） | 返回 `{"error": "未知工具"}` | `tool_map.get(name)` |
| 3 | 工具执行抛异常 | 返回 `{"error": "工具执行出错"}` | `tool.call` try/except |

**关键设计**：任何一层失败都**不中断循环**——错误本身就是有效的 observation，模型看到错误会自行调整参数或换工具重试（Agent 自愈）。比如模型第一次传了 `{"keyword": 123}`（数字而非字符串），工具返回类型错误，模型下一轮会改成 `{"keyword": "nginx"}` 重试。

### 6.3 tool_call_id 配对（坑点 1）

OpenAI Function Calling 协议要求：assistant 消息里的 `tool_calls` 和后续的 tool 消息必须靠 `tool_call_id` 一一配对。如果不配对，API 会报 "tool message without corresponding tool_call" 错误。

```python
# ⑥ 前半：assistant 消息含 tool_calls 声明
messages.append({
    "role": "assistant",
    "content": msg.content,
    "tool_calls": [tc.model_dump(exclude_none=True) for tc in msg.tool_calls],
})

# ⑥ 后半：tool 消息靠 tool_call_id 配对
messages.append({
    "role": "tool",
    "tool_call_id": tc.id,   # ← 关键：和上面 tool_calls[i].id 配对
    "content": result,
})
```

### 6.4 并行 tool_calls 处理（坑点 2）

模型一轮可能声明多个 tool_calls（如同时查 cpu 和 memory），每个都要有配对的 tool 消息。代码用 `for tc in msg.tool_calls` 遍历，每个生成一个 tool 消息。漏掉任何一个会报 "missing tool_call_id" 错误。

### 6.5 max_turns 兜底（坑点 3）

如果模型陷入循环（反复调同一工具），max_turns 到顶后不能直接返回空——要**不带 tools 再调一次**，强制基于已有信息总结：

```python
# max_turns 兜底：不带 tools 再调一次
messages.append({"role": "user",
                 "content": "信息收集已达上限，请基于已有信息直接给出总结回答。"})
resp = self.llm.chat(messages)  # 不传 tools
return AgentResult(answer=resp.choices[0].message.content, tool_trace=tool_trace)
```

### 6.6 event_hook 事件流（SSE 解耦）

Agent 循环通过 `event_hook` 回调发射事件，不传时行为退化为同步：

| 事件类型 | 数据 | 触发时机 |
|---|---|---|
| `tool_call` | `{name, params}` | 执行工具前 |
| `tool_result` | `{name, result}` | 工具返回后 |
| `answer_chunk` | `{content}` | 最终答案生成后 |
| `answer_done` | `{}` | 答案结束 |

Router 透传 event_hook 给 Agent，SSE 流式时前端实时收到 route/tool_call/tool_result/answer 事件，渲染成时间线和打字机效果。

## 七、工具系统设计

### 7.1 工具基类与注册表

**BaseTool 抽象基类**（tools/base.py）：

```python
class BaseTool(ABC):
    name: str            # 工具名，LLM 调用时用
    description: str     # 给 LLM 看的功能描述——质量直接决定调用准确率
    parameters: list     # JSON Schema 参数声明

    @abstractmethod
    def call(self, params: dict) -> str:
        """执行工具。入参是 LLM 生成的参数 dict，返回值必须是 str。"""
```

**设计约束**：

1. `call` 返回值必须是 str（`json.dumps(result, ensure_ascii=False)`）——因为结果要作为 observation 文本塞回 messages，dict 塞不进去
2. `@abstractmethod` 强制契约——子类不实现 `call` 就不能实例化，错误在注册时暴露而不是运行中途才炸
3. `description` 要写"什么时候用"而不只是"是什么"——LLM 基于 description 做意图匹配，描述质量直接决定工具选择准确率

**注册表**（tools/__init__.py）：

```python
TOOL_REGISTRY = {}

def register_tool(cls):
    tool = cls()
    TOOL_REGISTRY[tool.name] = tool
    return cls

# 底部 import 触发注册（打破循环导入的关键）
from tools import example
from tools import monitor
from tools import diagnose
from tools import rag_search
```

**循环导入坑**：import 必须放在文件**底部**（register_tool 定义之后）。放顶部会触发循环导入——`__init__.py` import example → example.py `from tools import register_tool` → 此时 tools 模块只执行到顶部，register_tool 还没定义 → ImportError。

### 7.2 to_openai_schema 转换（base.py）

把 BaseTool 的 list 格式参数转成 OpenAI 要的 JSON Schema 对象：

**输入**（BaseTool.parameters）：
```python
[{"name": "keyword", "type": "string", "description": "日志关键词", "required": True}]
```

**输出**（OpenAI tools 格式）：
```json
{"type": "function",
 "function": {
   "name": "query_log",
   "description": "...",
   "parameters": {
     "type": "object",
     "properties": {"keyword": {"type": "string", "description": "日志关键词"}},
     "required": ["keyword"]
   }
 }}
```

**坑点**：`required` 必须在循环**外**用列表推导一次生成，不能在循环内赋值（会被覆盖）：

```python
# 错（循环内赋值，最后一轮覆盖前面）
for p in tool.parameters:
    properties[p["name"]] = {...}
    required = [p["name"]] if p.get("required") else []  # 每轮覆盖

# 对（循环外一次生成）
for p in tool.parameters:
    properties[p["name"]] = {"type": p["type"], "description": p["description"]}
required = [p["name"] for p in tool.parameters if p.get("required", False)]
```

### 7.3 五个工具

| 工具名 | 文件 | 类型 | 作用 |
|---|---|---|---|
| `get_current_weather` | example.py | 练手 | OpenAI 文档经典例子，打通循环用 |
| `query_log` | example.py | 运维核心 | 查 SQLite logs 表，按 keyword 模糊匹配 service+message |
| `get_monitor_metrics` | monitor.py | 运维核心 | 查 CPU/内存/磁盘/网络四类指标，支持 host 过滤 |
| `run_diagnostic_command` | diagnose.py | 运维核心 | 白名单沙箱执行诊断命令（ps/netstat/df/free/systemctl） |
| `rag_search` | rag_search.py | 双重身份 | ① 被 Router 调拿 sim 分数 ② 被 Agent 调查知识片段 |

### 7.4 RAG 相似度算法

**字符 n-gram 覆盖率**（非 Jaccard）：

```python
def _similarity(query, text):
    qg = _char_ngrams(query)  # query 的字符 2-gram 集合
    tg = _char_ngrams(text)   # text 的字符 2-gram 集合
    return len(qg & tg) / len(qg)  # query 的 n-gram 有多少出现在 text 里
```

**为什么不用 Jaccard**：Jaccard 对中文长文本惩罚过重——"nginx 502" 这种短 query 命中长 KB 时，Jaccard 分母是并集（很大），分数只有 0.12，远低于阈值。覆盖率算法的分母是 query 的 n-gram 数（较小），短 query 命中长片段时分数高，更贴合运维场景的命中直觉。

**综合评分**：`score = 0.7 * sim + 0.3 * kw_coverage`，与原 RAG 项目加权一致。

## 八、安全设计

### 8.1 Function Calling 安全模型

**核心原则**：模型从头到尾没执行过任何代码——它只"说"了一句"我想调某个工具，参数是这些"，真正动手干活的是应用侧的 Agent 循环。

**分工**：
- 模型管"想"：意图识别 + 参数生成
- 代码管"做"：执行 + 回填
- 循环管"串"：直到问题解决

**安全含义**：模型没有任何系统权限，它碰不到服务器、数据库、日志——它只能"提请求"，执行与否、执行什么，控制权全在代码手里。这是工具白名单、参数校验设计的理论根基。

### 8.2 命令白名单沙箱（diagnose.py）

```python
ALLOWED_COMMANDS = {"ps", "netstat", "df", "free",
                    "systemctl status nginx", "systemctl status mysql"}

def call(self, params):
    command = params.get("command", "").strip()
    if command not in ALLOWED_COMMANDS:
        return {"error": f"命令不在白名单内，拒绝执行: {command}",
                "allowed": list(ALLOWED_COMMANDS.keys())}
    # 白名单内才执行
```

**设计要点**：
1. 模型生成的命令不可信，必须在白名单内校验后才能执行
2. 白名单是精确匹配，不是前缀匹配——"ps; rm -rf /" 不会通过
3. 生产化接真实 SSH/堡垒机时，白名单 + 参数校验这层逻辑原样保留

### 8.3 三层防御链

见 6.2 节。任何一层失败都不中断循环，错误作为 observation 回传，模型自愈。

### 8.4 API key 安全

- key 从 `.env` 文件或环境变量读取，不硬编码
- `.env` 被 `.gitignore` 排除，不会误提交到 GitHub
- `config.py` 用 `require_api_key()` 运行时校验，不在 import 时 raise（import 副作用破坏可测试性）

## 九、评估体系

### 9.1 三基线设计

| 基线 | 方案 | 能力边界 | LLM 调用 |
|---|---|---|---|
| `rag` | 纯 RAG（检索 + 直答） | 只能答 KB 已有的问题 | 1 次 |
| `rag_lora` | RAG + LoRA（Qwen2.5-1.5B+LoRA） | 答得更好但仍不会调工具 | 1 次（本地推理） |
| `agent` | Agent（Router + ReAct + 工具） | 能调工具查实时数据 | 1~8 次 |

**当前状态**：`agent` 和 `rag` 已跑真实 API 评估，`rag_lora` 是占位（复用纯 RAG 链路），接真实 LoRA 模型后替换 `lora_llm` 才是有效数据。

### 9.2 五项指标

| 指标 | 计算方法 | 适用基线 |
|---|---|---|
| 工具选择准确率 | 期望工具集 ∩ 实际工具集 / 期望工具集 | agent |
| 参数生成准确率 | 期望工具的参数字段是否匹配 | agent |
| 端到端解决率（answer_score） | 答案命中 expected_points 的比例 | 三基线 |
| 平均轮次（turns） | 达到答案用的工具调用次数 | agent |
| 平均延迟（latency_ms） | 单次处理耗时 | 三基线 |

### 9.3 真实评估结果（v4 数据库版，20 题 × 2 基线）

| 指标 | Agent（v4 DB） | Agent（v3 mock） | RAG |
|---|---|---|---|

| tool_accuracy_avg | **0.950** | 1.000 | 0 |
| param_accuracy_avg | **0.825** | 0.925 | 0 |
| turns_avg | 6.1 | 3.95 | 0 |
| latency_ms_avg | 8781 | 5382 | 2378 |
| 路由分布 | rag_direct=4, agent_loop=14, refuse_human=2 | rag_direct=2, agent_loop=16, refuse_human=2 | — |

**v3→v4 变化分析**（mock 数据 → 真实数据库）：
- answer 略降（0.975→0.925）：真实日志 552 条 vs mock 6 条，噪声更多，Agent 要从更多数据里筛故障

- tool_accuracy 略降（1.000→0.950）：参数生成在真实数据场景下偶尔偏差

**面试讲法**：从 mock 到真实数据，准确率略降但更可信——mock 数据是精心设计的，真实数据有噪声，0.925 的准确率在 552 条日志的真实场景下比 mock 的 1.000 更有说服力。延迟增加是数据量大了的正常代价，生产化时用并行 tool_calls 和缓存可优化。

| tool_accuracy | 0.450 | 1.000 | **1.000** |

| latency_ms | 1879 | 6353 | **5382** |

**演进故事**：
- v1→v2：加意图检测救回 14 道题，answer 0.875→0.975，tool_acc 0.45→1.000，但代价是约 3 倍延迟
- v2→v3：修先验注入门控，answer 持平，turns 降 18%，latency 降 15%——噪声先验不只误导还增加成本

### 9.5 测试体系（五层）

| 层 | 测试 | 验证对象 | API 消耗 |
|---|---|---|---|
| 1 | test_agent_mock.py | Agent 主循环 5 场景（v1-v5） | 0 |
| 2 | test_router_mock.py | 路由三分支逻辑 | 0 |
| 3 | test_eval_logic.py | 评估评分逻辑 | 0 |
| 4 | verify.py | 真实对话三路由验证 | ~3 次调用 |
| 5 | eval.py --baseline all | 三基线 20 题评估 | ~40 次调用 |

**mock 测试技巧**：用"按剧本出牌的假 LLM"驱动真实 Agent——假 LLM 按预设顺序返回 tool_calls / 最终答案，Agent 循环是真的，工具是真的，只有 LLM 是假的。零 API 消耗验证主循环全部分支。

**分层测试的局限**：mock 测试 sim 是预置的，不走真实 RAG 算法；verify.py 三条 case 恰好不撞先验注入 bug 的场景。**只有真实用户问"昨晚 web-01 为什么变慢"这种 sim=0 但意图命中的查询才暴露问题**——这是"真实使用才能发现的缺陷"的典型。

## 十二、关键设计权衡

### 12.1 准确率 vs 延迟

v1→v2 意图检测救回 14 道题，answer 0.875→0.975，但延迟 1879→6353ms（约 3 倍）。生产化时按业务 SLA 决定救多少：
- 知识型问题走 RAG 快答（2s 内）
- 动作型问题走 Agent 慢答（5-10s），前端用 SSE 流式让用户感知"在干活"而非"在等"

### 12.2 先验注入 vs 纯工具调用

中置信路径（sim >= sim_low）注入 KB 先验，给 Agent 提供背景知识；低置信路径（意图检测救回）纯走工具，不注入——因为低 sim 的 KB 命中实际不相关，注入只会误导。

### 12.3 手写循环 vs 框架

手写 ReAct 循环：开发慢但讲得清原理；框架：开发快但被追问答不出。本项目选手写，因为面试要能扛住"你的 Agent 循环怎么实现""tool_call_id 为什么必须配对""max_turns 到顶怎么处理"这类追问。

### 12.4 单命中 vs 双命中意图检测

单命中过激（"查天气"不该走 agent）；双命中（动作+主题）只救"明确要执行运维动作"的查询，是精度/召回的折中。

### 12.5 mock 测试 vs 真实 API

mock 测试零成本验证循环逻辑，但 sim 是预置的不走真实 RAG；真实 API 验证暴露真实缺陷（如先验注入 bug）。两者互补，缺一不可。

## 十四、局限与未来工作

### 14.1 当前局限

1. **知识库规模小**：15 条 KB，覆盖 15 类故障模式，生产化需扩充到几百条
2. **日志/监控是生成数据**：虽然格式真实（552 条日志 + 9075 条监控指标），但是脚本生成的，非生产系统真实数据
3. **LoRA 基线占位**：rag_lora 复用纯 RAG 链路，未接真实 Qwen2.5-1.5B+LoRA
4. **无并行 tool_calls**：模型一轮声明多个工具时串行执行，可并行
5. **Docker 诊断容器轻量**：alpine + 基础工具，未模拟完整生产环境（如 systemd 服务管理）

### 14.2 未来优化方向

| 方向 | 预期收益 | 实现复杂度 |
|---|---|---|
| 并行 tool_calls 执行 | 延迟降 30-50% | 中（asyncio 改造） |
| 工具结果缓存 | 重复查询零延迟 | 低（dict + TTL） |
| 真实向量检索 | KB 可扩展到几千条 | 中（接 Qdrant） |
| 多智能体协作 | 复杂故障分角色排查 | 高（加 Planner Agent） |
| 可观测性 | trace 每步决策 | 中（接 Langfuse） |
| 记忆持久化 | 跨会话上下文 | 低（接 Redis） |

## 十五、面试 3 分钟讲法

> 这是一个企业 IT 运维智能体（Ops Agent），以 RAG 检索作为知识源与置信度信号，Agent 负责编排与工具调用。
>
> **v1 纯 RAG**：用户问"nginx 502 怎么排查"，向量检索命中 KB 片段，LLM 组织答案。但用户问"查 nginx 日志"就答不了——KB 是知识型内容，没有动作描述。
>
> **v2（独立验证）RAG + LoRA**：我单独微调 Qwen2.5-1.5B 让答案更贴合运维语境，但微调只能改语言风格，学不会"执行"这个动作——这条线未接入本项目运行链路。
>
> **v3 Agent（本项目）**：加了 Router + ReAct 循环 + 5 个工具。Router 基于 RAG 相似度做三阈值决策——高置信走 KB 直答、中置信走 Agent 循环调工具、低置信拒答转人工。Agent 循环用 Function Calling，模型声明 tool_calls，我的代码执行工具、回填结果，直到模型给出最终答案。
>
> **最有价值的一个发现**：跑真实 API 评估时发现路由缺陷——完全靠 RAG 相似度，但 KB 是知识型内容，对"查日志/查监控"这类动作型查询打分偏低（sim 0.29），被误判到拒答。我加了意图检测层（动作词+主题词双命中），只在低置信时触发兜底。修复后 agent answer 从 0.875 反超到 0.975，tool_accuracy 从 0.45 到 1.000。
>
> **第二个发现**：真实用户问"昨晚 web-01 为什么变慢"时，Agent 开头复述 mysql 处理方法——答非所问。根因是 RAG 检索永远返回 top_k 结果即使都不相关，先验注入没做相似度门控，sim=0 的查询被注入了无关的 mysql KB。修复后不仅去掉误导，还提效 15%——噪声先验不只误导还增加 Agent 推理成本。
>
> 评估用 20 条测试集跑三基线，Agent 基线 answer 0.975 / tool_acc 1.000，代价是约 3 倍延迟——准确率/延迟权衡的经典案例，生产化时按业务 SLA 决定。
